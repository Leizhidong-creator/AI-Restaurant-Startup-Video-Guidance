# 知识库与案例机制 · 设计说明（KB · Skill · 信任 · 匹配）

> 定位：这是 `PRD.md` 中 **§8.3（案例解构）、§8.6（专家知识底座/RAG/Skill）、§8.8（个体迁移）、§8.9（复盘）** 的**设计细化**，供折进 PRD 或独立参考。
> 日期：2026-07-22
> 目的：把"产品边界（什么算运营）、知识库装什么、案例怎么对用户讲、用户凭什么信、案例怎么和用户情况匹配触发"这几件事定死，避免建库和前台表达跑偏。

---

## 1. 一句话定位：KB 管"知道什么"，Skill 管"怎么想/怎么做"

通用大模型有两个缺陷——**不知道**（缺真实依据，爱说空话/编数字）和**不会按专家路子想**（被动、乱答、跳步、过早下结论）。

- **知识库 / RAG**：补第一个。提供**内容/证据**——可迁移判断规则 + 真实案例。
- **分析 Skill（决策内核）**：补第二个。提供**流程/行为**——问题树、追问顺序、观察顺序、工具时机、结论门槛、结束条件。
- **关系**：Skill 是驱动、KB 是弹药。Skill 的当前步骤决定去 KB 检索什么，不是把 KB 一股脑丢给模型。
- **分工口诀**：视频理解=看见，RAG=知道，Skill=思考，实时连麦=追问指导，复盘=形成行动；确定性计算（保本线/回本/现金跑道）=**规则引擎**，AI 不心算。

> ⚠️ 差异化不来自"话题/维度"，来自**背后有没有一个像餐饮专家这样的真实角色**（battle-tested 的判断心智模型 + 能点名的真实案例 + 可信身份）。这是通用模型对**任何**维度都给不了的。选址、运营都一样：去掉真实角色 → 都退化成通用内容；带上角色 → 都能极差异化。**所以护城河本质是"角色采购"问题**——你能 source 到多少个可信真实角色 × 多少维度的判断和案例。

## 2. 产品边界：什么算"运营"、什么归餐饮专家核心（判断型 vs 执行型）

决定一件事"归不归餐饮专家核心"的，**不是它落在生命周期哪个阶段，而是它是"判断型"还是"执行型"**。

| | 判断型 | 执行型（≈ 狭义"运营"） |
|---|---|---|
| 问的是 | 该不该做 / 能不能成 / 为什么不行 / 救不救得活 / 坑在哪 / 止损还是继续 | 具体怎么做：出餐提效、服务、复购/私域、抖音引流、成本控制、招人 |
| 覆盖 | **横跨全生命周期**（开店前 ~ 在营 ~ 危机） | 主要在"在营"阶段的日常优化 |
| 归属 | **餐饮专家的线 = 产品脊柱 + 护城河** | **缺角色、通用性高（暂不作为指导层做）** |

**严格定义（项目统一尺子）：**
- **运营（狭义）= 在营店铺的日常执行型优化**（出餐/服务/复购/引流/成本/人）。
- **开店 ≠ 运营**：是"决策 + 筹建"。其中"要不要开 / 开哪 / 加盟是不是坑 / 单店能不能回本"= **判断型（核心）**；"装修/招人/菜单具体怎么弄"= 执行型（薄）。
- **救活 ≠ 运营**：快倒闭起死回生，主体是"危机诊断 + 止损/投入决策"= **判断型**，恰是餐饮专家最强区之一（赔钱复盘），**属核心，别误归进"缺角色的运营"**；只有"救活之后日常具体怎么改"那一截，才落到执行型。

**含义：** 产品脊柱 = **判断型 · 全生命周期**（开店决策 + 在营诊断 + 危机止损/转向）；真正"缺角色"的只有**执行型运营 how-to**（日常怎么做得更好），暂用"证伪薄片 + 诚实说不确定"兜住（见后文"没命中就别硬套"），**不为它补第二个角色**。

> 若将来要扩运营层：本质是"能不能 source 到一个真实的运营操盘手角色"。抖音候选（待核实内容密度与授权）：**乐姐**（偏经营/营销/爆店）、**比尔盖南**（供应链+全链路）、**柴大官人**（探店/解析品牌为什么走红，最贴"案例解构"）。GitHub 上没有现成的"运营知识 skill"可直接用（只有 SaaS/管理工具类），仍需自建。

## 3. 知识库到底装什么（规则 + 案例证据两层，不是通用方法）

按差异化价值从高到低：

```
知识库
├─ 可迁移判断规则(心智模型)   ← 骨架，能泛化评判"没见过的组合"
│    例：人流≠客流；低租金可能是失败信号；加盟先查直营店
└─ 真实案例 + 后果数字(证据)   ← 每条案例绑定"它印证了哪条规则" + 时间点 + 来源
     例：体育馆门口面馆，看中人流，开一个月收入 300 → 印证"人流≠客流"
```

**规则是骨架、案例是让骨架可信/可追溯/能打脸/能迁移锚定的证据**，两者是"规则←→证据"的绑定，不是二选一。

**不该重仓的东西**：
- 通用计算方法/公式（保本公式等）——通用模型基本已会，**零差异化**；且计算本身归**规则引擎**。
- 品类通用经验参数（房租占比、客单价区间）——可进库，但属**低差异化层**，不是护城河核心。

> 结论：知识库 = **这位专家的可迁移判断规则（骨架）+ 支撑规则的真实案例与数字（证据）**。只装通用方法、丢掉真实案例，产品会退回"又一个通用问答"。

## 4. 案例怎么对用户讲：第一人称"过来人"口吻，不引用出处

### 4.1 表述改法

- ❌ 引用口吻：「餐饮专家在《开店避坑》视频里讲过，有个体育馆铺面……」
- ✅ 过来人口吻：「你这情况我见过——之前有个也是看中人流大、在体育馆门口开的，开了一个月，收入才 300 块。」

**为什么 ✅ 更强**：出处对 C 端用户是无效信息（不查、也证明不了）；第一人称"相似案例"有代入感、直接服务"个体迁移"；**顺带帮了去标识**（不用点名真人、不甩可查链接）。

### 4.2 两条不可破的线

1. **口吻可以改，数字和案例必须是真的**。「收入 300 块」必须来自 KB 里真有的一条案例，只是换成第一人称复述。**"用户不验证" ≠ "可以现编"**——因为：评委会查、被拆穿一次信任归零、违背借餐饮专家真实内容的授权。**框架换的是"怎么讲"，不是"是不是真的"。**
2. **"跟你很像"必须是同维度真匹配**（都踩"看中绝对人流"这个坑），不是"都开奶茶店"的表面个性化。

## 5. 用户凭什么信（可追溯性不是用户信任杠杆）

**先认掉一个事实**：C 端用户不会核实、也证明不了你有没有编，真案例和编的在他眼里一样。所以"有据可查/可追溯"**不是给用户的信任杠杆**——它是给**评委**（会追问出处）和**开发质检/授权**的。要分清此刻面对的是哪种"用户"。

**C 端用户的信任真正靠这几样（他能"感觉到"的）：**
- **看现场**：实时连麦真看了"我的"铺子、回应了我镜头里的东西——"它真在看我，不是套模板"。这也是 PRD 把连麦当内核的隐藏理由。
- **反直觉打脸的"啊，对哦"**：把我以为对的（人流量大）掰成坑、逻辑一听就通，比任何数字都建立信任。
- **敢说不确定**：会说"证据不足、你得去验证"的顾问比永远信心满满的更可信。诚实是信任杠杆。
- **把"信我"换成"你自己去验证"（最有效）**：给一个低成本自证动作——"明晚 18–20 点去数真进店的人"。用户自己验证完，信任是他给自己建的，绕开"你会不会编"。
- **真人 IP 背书**：餐饮专家是用户可能本就认的真人，可信度转移过来。

**前台策略**：证据脚注**少露给用户**，力气放在"戳中 + 看现场 + 可自证的下一步"；**可追溯性留给答辩和开发质检层**。

## 6. 案例 ↔ 用户情况：怎么判断匹配、怎么触发

### 6.1 核心：别"用户↔案例"直接比，用"判断规则/诊断维度"做连接键

直接比会退化成"都开奶茶店"的表面匹配。正确路径：

```
用户情况 → 命中哪条判断规则(诊断维度/风险信号) → 取该规则绑定的真实案例 → 第一人称讲出来
```

"像"的不是品类，是**用户正在踩的那个坑**。规则本身定义了对照维度，所以规则=连接键，天然保证"同维度对照"。

### 6.2 怎么算"命中"（三层，从可靠到兜底）

- **A. 结构化触发条件（主）**：每条规则带一组 tags（维度 + 用户信号 + 条件）。Skill 把用户情况也结构化进**同一套标签空间（= 8 个诊断维度）**，逐维度比。可靠、可解释。
- **B. 语义召回（补漏）**：结构化没覆盖到的才做向量检索；**检索问题由 Skill 按"当前诊断维度"生成**，不是拿用户原始文本去搜（避免按"奶茶/大学城"词表面命中）。
- **C. LLM 复核当闸（防假匹配）**：取到候选后模型判断一句"**这条案例的坑，是不是用户正在踩的坑？**"——是才讲，否就丢。把"topic 像"过滤成"机制像"。

### 6.3 什么时候触发

不是一次性搜全部，而是 **Skill 状态机逐维度触发**：案例解构列出风险变量 → 连麦追问/个体迁移时用户每补一个事实就结构化进标签 → 命中某维度风险规则 → 立刻牵出绑定案例。命中在哪个维度，就讲那个维度的相似案例。

### 6.4 一条纪律：没命中就别硬套

用户情况没有任何规则真命中时，按纪律说"我没见过特别像的 / 这点证据不足，你得去验证"，**宁可不讲案例也不硬凑**——硬凑就是假个性化，一眼看穿反而砸信任。落在决策内核 `validate_judgment`（禁止未知证据/纯推断的强结论）上。

## 7. 落地字段模板（扒字幕建库时照着填）

每条案例分三段存：

```
【对用户的复述（前台）】
  相似情境：一句话点出"跟谁像"——品类/位置类型/看中点   例：看中人流、在体育馆门口开小吃
  结局一句话：具体、有冲击                              例：开一个月，收入才 300 块
  第一人称模板："你这情况我见过，之前有个也是{相似情境}，结果{结局一句话}。"

【触发条件（匹配用·tags）】
  诊断维度：{8 维之一}                                 例：位置与真实动线
  用户信号：{命中该案例的关键信号}                     例：看中"人流量大" + 位置=过路型
  印证规则：{绑定的判断规则}                           例：人流≠客流

【开发证据（答辩/质检层，不摆给用户）】
  真实出处：原视频 + 时间点                            例：视频X 00:12–00:20
  来源/审核状态：evidence_grade = reviewed|golden
  后续经营结果：⚠️ 当前 5 个 golden 案例普遍缺这项，需补
```

> 标签空间 = 那 8 个诊断维度（经营事实、单店经济账、风险承受力、动机与能力匹配、信息来源与验证、位置与真实动线、顾客需求与竞争、经营模型与退出）。用户情况和案例触发条件都用这一套维度对齐。

## 8. 对现有实现的落点（不用造新东西）

- **KB（`engine/decision_core/knowledge/platform.jsonl` 等）**：每条规则/案例加「触发条件 tags」+「对用户复述」两段字段。
- **Skill（决策内核 `RestaurantSkillProvider` / `DecisionRuntime`）**：把用户情况结构化进同一套 8 维标签；逐轮判断命中；`validate_judgment` 把关"没证据不硬说"。
- **复盘/前台（§8.9、§11.6 复盘页）**：弱化证据脚注，强化"针对你的判断（第一人称相似案例）+ 可自证的下一步"。

## 9. 现状风险（诚实）

- 平台 KB 现 93 条（2026-07-23 实查：reviewed 52 / golden 25 / secondary 16），但 **kind 全部为规则/方法，案例条目（kind=case）为 0**——本文最强调的"证据层/结局数字"整层缺席。**第一优先级是补带真实结果的案例**（执行清单见 §11），而不是再堆通用方法。
- 没有真实结局数字，第 4 节的"过来人第一人称讲结局"就无米下锅、只能空讲——所以建库时**结局一句话 + 后续结果是必填**。
- 运营层缺角色（餐饮专家运营内容已确认不密）。按 §2 的边界：判断型的"救活/止损"仍归核心（餐饮专家能干），执行型运营 how-to 暂不做；要扩再按"角色采购"逻辑评估候选人。

## 10. 环境兼容实测（摄像头 / getUserMedia）

实时连麦是 P0 内核，但入口是"扫码进抖音/微信"，内置浏览器对摄像头支持不一。已实测（2026-07-23）：

| 环境 | 仅视频 | 视频+麦克风 | 结论 |
|---|---|---|---|
| 微信 · 安卓 | ✅ | ✅ | 可用 |
| 抖音内置(TTWebView) · 安卓 | ⚠️ getUserMedia"成功"但画面空白（拿到流、无实际帧） | ❌ NotReadableError | 不可用 |
| 微信 / 抖音 · iOS | 待测 | 待测 | 待测（iOS 历史重灾区，重点补） |

**应对（产品 / 前台）：**

- 检测到抖音内置浏览器（UA 含 `BytedanceWebview` / `TTWebView`）→ 提示"右上角 ··· → 用系统浏览器打开"，不在此环境直接连麦。
- **前端验收硬要求：摄像头可用性以"画面真出帧"判断**（getUserMedia 成功后播放，校验 `video.videoWidth > 0`），**不能只看 promise resolve**——否则会被抖音"成功但空白"误导，用户看到空屏还以为正常。
- 微信（至少安卓）可用，微信渠道相对 OK。
- 长期要在抖音生态内稳定用摄像头 → 抖音小程序（有正规相机 API），纯网页在抖音 WebView 里做不到。
- 答辩 demo：不演"抖音里扫码直接连麦"；用系统浏览器 / 微信安卓 / 自备设备的 Chrome·Safari（呼应 PRD §17.4）。

## 11. 案例层采集执行清单（调研版，照此做即可开工）

> 为什么现在补案例最划算：服务端注入管道已接通并实测生效（连麦前四维解构、连麦中 assist 自动查 KB 注入，PRD §23 2026-07-23）——**案例写进 platform.jsonl → importer 导入 → 立即流进对话**，不需要再动任何代码。

### 11.1 目标与缺口

- 现状：93 条全是判断规则/方法，**案例条目 0 条**。
- 首批目标：**24 条 planning 阶段案例**（8 个诊断维度 × 每维 ≥3 条），品类优先 **奶茶 / 咖啡 / 小吃**（线上预热的三个演示品类，评委最可能点到）。

### 11.2 源料从哪来（按可信度排序）

1. **原始视频（导师抖音账号）**：证据本体。案例必须最终锚定到"原视频 + 时间点"。
2. **本地参考 Skill 仓库**（`1.演示过程材料/2.阶段二：展开制作/成员二-餐饮知识库RAG与Skill/参考Skill仓库/`，本地 not in git）：11 个外部整理者已扒好的 transcripts / case_studies，**当目录用**——从中快速定位候选案例，再回原视频核对时间点与数字。⚠️ `source_url` 必须写原视频链接，不得把二手仓库当证据本体；未回看原视频前 evidence_grade 只能标 `secondary`。
3. 现有 93 条规则的 `source_url`/`source_locator`：很多规则本身就萃取自某个案例视频,顺藤摸瓜能找到"带结局"的原始故事。

### 11.3 字段映射（§7 三段 → platform.jsonl，importer 直接可导）

| §7 模板段 | jsonl 字段 | 写法要点 |
|---|---|---|
| — | `knowledge_id` | `case-{品类或情境slug}-{三位序号}`，如 `case-tea-mall-001` |
| — | `kind` | **`case`**（importer 已支持，缺省才是 knowledge） |
| 结局一句话 | `title` | 直接用结局句："体育馆门口小吃店，开一个月收入 300 块" |
| 对用户的复述(前台) | `content` | 相似情境+结局，**用用户会说的口语词写**（检索是词面 bigram 匹配：写"房租""人流""加盟费"，别写"固定成本支出""动线通量"）|
| 触发条件 tags | `topics` | 8 维标签 ≥1 + 品类 + 用户信号词（如 `位置与真实动线`、`奶茶`、`人流量大`）|
| 诊断维度→场景 | `stages` | planning 案例填 `["planned_opening","site_selection"]` 等 |
| 真实出处 | `source_url` + `source_locator` | 原视频链接 + `mm:ss–mm:ss` 时间点 |
| 来源类型 | `source_type` | `public-video-transcript-reviewed`（回看核对后）|
| 审核状态 | `evidence_grade` | 见 11.4 晋级规则 |
| 迁移边界 | `limitations` | 必填："哪些情况不适用"（如"商场店逻辑，不适用街边档口"）|

### 11.4 质检门（缺一不入库）+ 晋级规则

**必填四件**：① 结局数字（收入/亏损额/回本月数，没有具体数字的故事不收）② 原视频时间点 ③ ≥1 个 8 维标签 ④ limitations 写清不适用边界。

**evidence_grade 晋级**：二手仓库摘来未核对 = `secondary`（只作发现线索，最终判断不可用）→ 回看原视频核对数字与时间点 = `reviewed`（可进最终判断）→ 另有后续经营结果佐证（如后续视频回访）= `golden`。

### 11.5 单条工作流（约 15 分钟/条）

1. 在参考仓库 case_studies / transcripts 里挑一个"有具体结局数字"的故事;
2. 回原视频核对：数字、时间点、当事人情境（品类/位置/投入）;
3. 按 11.3 填一条 jsonl（先在分支/本地文件攒批,不直接改 platform.jsonl）;
4. 自检 11.4 四件套 → 过则并入 `platform.jsonl` + `manifest.json` 版本 +1;
5. `pocketmentor-import-platform-kb` 重导 → 用一句"用户信号"话术在 `/skill/advance` 试触发,确认能被检索命中。
